## Phase H evidence and diagnosis

The six independent reports agree on a historical snapshot of 94 completed, 23 pending, 4 claimed, 0 failed. They do not establish current state or imply that all visible submissions completed. The observed failures separate into:

- Client context continuity: some claim responses did contain the token, but a later tool call could not reuse it after only a redacted summary was retained. Code Mode continuation failures were reported at the orchestration layer.
- Correct Core fences: a stale Group 11 token used for Group 60 progress was rejected. A repeated request ID produced `request_id_conflict`; a malformed progress UUID was rejected. These are evidence that validation worked, not evidence that Core lost or accepted a stale token.
- Positive controls: several workers completed progress and submit calls, including 31 visible successful submissions by Worker 0003. Worker 0005's later `get_task` read showed Group 60 completed after an earlier status response showed it claimed; the cause was unverified and does not establish a database race.
- Unknowns remain unknown: some reports lack a visible full tool response, and successful `submitted` responses do not individually prove that the later Completion Action finished.

Conclusion: the high-confidence defect is that the ordinary model workflow depends on a short-lived, manually carried lease token plus request UUID/sequence values across stateless calls. The available evidence does not justify weakening Core's attempt fence, replaying uncertain side effects, or changing accepted results.

## Proposed minimal trusted API

The six ordinary operations are `claim`, `progress`, `complete`, `release`, `resume`, and `status`. Their public Relay names will be `coord_claim`, `coord_progress`, `coord_complete`, `coord_release`, `coord_resume`, and `coord_status`; Core JSON-RPC will use a separate `scheduler/trusted_*` namespace. Existing ten Relay tools and old HTTP/MCP methods stay available as the compatibility path.

| Operation | Ordinary inputs | Result and state rules |
| --- | --- | --- |
| `claim(batch_id, worker_id)` | Exact batch and four-hex collaboration label; optional lease duration only where policy permits. | Atomically returns the existing live task for this worker if one exists; otherwise claims one ready task only from this batch. Response contains task and current `attempt_no`, never the lease token. A repeated call after a lost response returns that same assignment. |
| `progress(worker_id, task_id, attempt_no, checkpoint)` | Current task and generation from `claim`/`resume`, plus a bounded non-empty checkpoint. | Core checks batch, worker, `state=claimed`, matching task and generation, and live lease; it stores the checkpoint and allocates the next sequence/request ID. Identical retry of the latest checkpoint is idempotent. Progress renews only according to the batch lease policy and remaining budget. |
| `complete(worker_id, task_id, attempt_no, result, ack?)` | Current task/generation and bounded JSON result. | Core atomically accepts or submits through the existing validator path. Same generation plus same accepted result reconciles to the existing outcome; a changed result conflicts. Completion Actions stay in the existing transactional outbox and are not re-enqueued. |
| `release(worker_id, task_id, attempt_no, reason?)` | Current task/generation; reason is bounded and optional. | In one transaction, only the matching live claimed attempt can be released. It becomes pending with capped interruption backoff, the internal fence is invalidated, and the business failure count does not change. Terminal or reassigned attempts return an explicit conflict. |
| `resume(batch_id, worker_id)` | Exact batch and collaboration label. | Read-only. Returns that worker's current task/checkpoint/generation, or a durable `released`, `expired`, `reassigned`, `submitted`, `completed`, or `empty` disposition. It never claims or steals work. |
| `status(batch_id, worker_id?)` | Batch and optional worker label. | Returns a transaction-consistent batch snapshot with distinct pending/claimed/submitted/terminal counts, interruption/attention indicators, and optional worker attempt. `active` remains an aggregate scheduling count, not model liveness. |

For `progress`, `complete`, and `release`, the plan's terse examples omit `attempt_no`; the implementation will carry this **non-secret integer generation** returned by `claim`/`resume`, alongside task ID. It is not a bearer credential or generated request UUID. Requiring it is the least extra input that lets Core reject a stale attempt even when the same trusted `worker_id` later reclaims that task. Core continues to keep the actual lease token private to its persisted task row.

The Relay derives `agent_id` from the authenticated owner-bound worker label; the label remains a collaboration tag, not proof of a distinct ChatGPT conversation. Every trusted request remains bound to the exact batch and allowed scope. OAuth refresh changes access-token state, not durable Core assignment state. If one worker already has multiple legacy active claims, `resume/status` returns all with an explicit conflict requiring resolution rather than silently picking one.

## State, migration, and recovery contract

1. **Generation versus failure budget.** Keep `attempt_no` monotonically increasing and preserve every existing value. Keep `attempt_count` as historical claim count; stop using it as the new retry gate. Add `failure_count` as a separate counter incremented only for actual execution/validation failure. Business claim eligibility becomes `failure_count < max_attempts`. On additive migration, conservatively initialize pending/terminal rows from their historical count and active claimed rows from `max(attempt_count - 1, 0)` because the live attempt has not yet failed. No existing counter is cleared. Explicit manager retry grants another failure budget without resetting lifetime attempt history.
2. **Interrupted attempts.** `release` and lease expiry atomically close the attempt as interrupted, preserve checkpoint, clear the live token, and requeue with capped exponential backoff based on an interruption streak. Real progress resets the consecutive streak. The streak saturates at a configured bound and sets a visible `needs_attention` indicator; it does not increment `failure_count` or become a business failure. Existing `retry_backoff_ms` / `max_backoff_ms` apply unless a test shows a separate policy is needed.
3. **Atomic fences.** The task row and `task_attempts` row update in the same SQLite transaction. Writes require exact task, batch, worker, current attempt number, claimed state, and unexpired lease. `release`, `complete`, `cancel`, and reclaim races have one winner. Old attempt numbers cannot change progress, accepted result, or action outbox. Legacy token methods retain their existing token, agent, receipt, and lease checks.
4. **Resume after restart.** Core DB state is the source of truth. `resume` reads the latest durable worker attempt and checkpoint; no MCP-process vault is required. On process restart, the regular reclaimer still handles expired leases. If another worker has reclaimed the task, resume returns `reassigned` plus safe checkpoint state and does not restore the old fence. A repeated completion reads the task/attempt receipt and result hash before deciding; a timeout never blindly reruns a validator or action.
5. **Migration safety.** Add only columns/tables/indexes and transactionally backfill rows whose current owner/generation can be read from the existing task. Preserve task/result/ack/receipt/action tables and all old columns. Existing rows with no provable owner remain without fabricated attempt history. Run old-schema fixture migration and `PRAGMA integrity_check`; rollback is restoring the pre-upgrade DB and old binary, not opening a migrated DB with old code.
6. **At-least-once execution boundary.** Scheduling can be repeated after context loss. External file, command, message, or other side effects remain the executor's responsibility to isolate and make idempotent. Core's completion receipt/outbox prevents duplicate accepted completion events; it does not promise exactly-once external execution.
